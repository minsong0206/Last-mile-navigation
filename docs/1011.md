# 2026-10-11 세션 분석 — 조향 편향의 정체 규명

실외 실주행 로그 41개(주행 틱 3995개) + 실내 teleop 측정으로, 오늘까지 "좌편향"이라고
뭉뚱그려 부르던 현상을 **서로 다른 4개 원인**으로 분해했다. 결론부터:

| 원인 | 정체 | 해결 상태 |
|---|---|---|
| 1 | angular 명령이 **0.01 단위로 절삭(truncate)** | 디더링으로 해결 (`--enable_angular_dither`) |
| 2 | **하드웨어 좌편향** = 트림 **-0.051** | 실측 확정, `--angular_trim` |
| 3 | **모델 자체의 좌편향** (+0.0115 중앙값) | 미해결 — 재학습 영역 |
| 4 | 모델의 **우회전 권한 부족** (좌회전의 41~72%) | 완화책 구현 (`--angular_right_gain`), 근본은 재학습 |

핵심 교훈: **1번을 모르는 상태에서 2번을 측정하려 해서 하루를 썼다.** 0.01 미만 해상도의
트림 조정이 전부 무효화되고 있었기 때문에, 소수점을 쪼개도 결과가 안 변했다.

## 1. angular 명령의 0.01 단위 절삭 (가장 중요한 발견)

### 증거

실측에서 다음 패턴이 반복 재현됨:

| 보낸 값 | 실제 주행 |
|---|---|
| -0.050 | 좌 |
| -0.055 | 좌 |
| -0.058 | 좌 |
| -0.059 | 좌 |
| **-0.060** | **우** |

`-0.050`~`-0.059`가 **전부 동일하게 동작**하고 `-0.060`에서만 바뀐다. 이는 로봇(또는
펌웨어)이 angular를 **0 쪽으로 절삭**함을 뜻한다 — `-0.059` → `-0.05`, `-0.060` → `-0.06`.

**결정적 근거**: 경계가 `linear=0.2`(실내)와 `linear=0.3`(실외) **양쪽에서 똑같이 -0.06**
이었다. 진짜 물리적 균형점이라면 속도에 따라 이동해야 하는데 움직이지 않았다 → 물리값이
아니라 **양자화 경계**다.

### 절삭 위치

SDK 경로를 추적한 결과 **우리 쪽 코드에는 반올림/절삭이 없다**:

```
/control (main.py) → browser_service.send_message() → basicRtm.js: JSON.stringify(json)
                   → Agora RTM → 로봇 펌웨어
```

`main.py:554`에서 `body.angular`를 그대로 넘기고, `basicRtm.js:81`의 `sendMessage()`도
`JSON.stringify` 후 RTM으로 그대로 전송한다. 따라서 **절삭은 로봇 자체 펌웨어에서** 일어나며
레포에서 확인/수정 불가.

### 해결: 델타-시그마 디더링

제어 루프가 3Hz이고 로봇 yaw 반응은 그보다 훨씬 느리므로, 인접한 두 양자화 단계를 섞어
보내면 로봇은 **시간평균**을 느낀다. 매 틱 양자화 잔차를 다음 틱에 넘기는 방식:

```python
steps = math.trunc(round((desired + accum) / q, 6))   # round()로 부동소수 오차 제거 후 절삭
sent  = steps * q
accum = clip(accum + (desired - sent), ±2q)
```

검증 (60틱 = 20초 @ 3Hz):

| 요청 | 실현 평균 | 사용 단계 |
|---|---|---|
| -0.050 | -0.05000 | [-0.05] |
| -0.052 | -0.05200 | [-0.06, -0.05] |
| -0.055 | -0.05500 | [-0.06, -0.05] |
| -0.059 | -0.05900 | [-0.06, -0.05] |
| -0.063 | -0.06300 | [-0.07, -0.06] |

오차 0으로 수렴. **이제 0.001 단위 조정이 실제로 반영된다.**

CLI: `--enable_angular_dither`, `--angular_quantum`(기본 0.01). 기본 꺼짐.
`deployment/pure_teleop_straight_test.py`에도 동일 로직 추가 + 종료 시 평균 검증 출력.

## 2. 하드웨어 좌편향 = 트림 -0.051 (실측 확정)

### 측정 방법

디더링을 켠 `pure_teleop_straight_test.py`로 **모델을 완전히 배제**하고(`angular=0 + 트림`만
전송) 실내 바닥 기준선 대비 이탈을 측정. 곡률 `κ = 2y/d²` (y=횡방향 이탈, d=주행거리,
좌회전 양수).

| 트림 | 주행거리 | 이탈 | 곡률 κ (1/m) |
|---|---|---|---|
| -0.055 | 3.36m | 우 20cm | -0.03543 |
| -0.045 | 6.00m | 좌 80cm | +0.04444 |
| -0.0506 | 6.00m | 좌 10cm | +0.00556 |

3점 최소제곱: `κ = 7.94 × cmd + 0.4035` → **0 교차 = -0.0508 ≈ -0.051**

주행거리가 3.36m / 6.00m로 크게 달랐지만(루프 끊김 탓) **계산에는 영향 없다**. κ는
"움직이는 동안의 각속도 ÷ 속도"라서 멈춰 있던 시간 비율과 무관하기 때문.

### 부산물: 명령 → 곡률 변환계수

**7.94 /m per unit angular command.** 이 값이 있으면 앞으로 **이탈거리만 재면 트림 보정량을
계산으로 바로** 뽑을 수 있다(이분 탐색 불필요):

```
보정량 = -κ_측정 / 7.94 = -(2y/d²) / 7.94
```

### 측정의 한계

- 실내 매끄러운 바닥에서 측정 — 실외 보도는 마찰/접지가 달라 미세하게 어긋날 수 있음
- 재현성 한계는 **6m 주행에서 약 10cm**(≈ 트림 0.0007). 그보다 세밀한 조정은 노이즈 추적
- `linear`은 SDK에서 **-1~1 정규화 값**(코드 주석의 "m/s"는 부정확). `linear=0.3`에서 실측
  속도는 약 0.11~0.20 m/s로 run마다 달랐다(루프 끊김 영향)

## 3. 모델 조향 분석 (주행 틱 3995개)

### 방향은 정상이다

필요 회전량(`heading_route_diff_deg = heading - route_bearing`, 음수=좌회전 필요)과 모델
출력의 상관계수 **r = -0.668** — 부호가 정확하고 비례 반응한다.

| 필요 회전 | 모델 angular 평균 |
|---|---|
| 좌 60°+ | +0.184 |
| 좌 30~60° | +0.120 |
| 좌 10~30° | +0.067 |
| 직진 (±10°) | +0.012 |
| 우 10~30° | -0.027 |
| 우 30~60° | -0.087 |

즉 **"모델이 회전을 못 한다"는 이전 진단은 틀렸다.** 모델은 회전을 인식하고 올바른 방향으로
조향한다.

### 문제 1: 우회전 권한 부족 (비대칭)

**같은 크기**의 회전 요구에 대한 좌/우 출력 비교:

| 요구 회전량 | 좌회전 \|angular\| | 우회전 \|angular\| | 우회전 세기 |
|---|---|---|---|
| 10~30° | 0.0668 (n=40) | 0.0272 (n=68) | **41%** |
| 30~60° | 0.1202 (n=61) | 0.0865 (n=39) | **72%** |

상수 트림은 전체를 균일하게 이동시킬 뿐이라 이 비대칭을 고칠 수 없다 → 모델 출력이
음수(우회전)일 때만 증폭하는 `--angular_right_gain` 구현(실측 기준 1.4~2.4배 필요, 1.8 권장).
**근본 원인은 학습 데이터 클래스 불균형으로 추정되며 재학습 영역.**

### 문제 2: 모델 자체의 좌편향

직진 구간(±10°, 전체의 94%)에서도 모델이 **+0.012**를 지속 출력한다. 변환계수를 적용하면:

```
cmd = -0.051(트림) + 0.0115(모델) = -0.0395
κ = 7.94 × (-0.0395) + 0.4035 = +0.090 /m
→ 6m 주행 시 좌측 1.6m 이탈
```

**모델 출력은 작지 않다** — 잔여 트림 오차(10cm)의 16배 크기로 궤적을 휘게 한다.
하드웨어 편향(2번)과 분리된, 모델 자체의 문제다.

### 분석 신뢰도 단서

- 오늘 데이터의 **94%(3752/3991틱)가 직진 구간**. 회전 데이터는 239틱뿐(버킷당 39~68틱)
- 60°+ 우회전 버킷은 **전부 오프라인 스모크 테스트의 합성 데이터**(값이 모두 동일한
  -0.0262)였으므로 위 표에서 제외함

## 4. 정정: "트림이 모델을 묻는다"는 중간 진단

세션 중간에 "트림(0.055)이 모델 출력(중앙값 0.0115)의 4.8배라서 모델이 묻힌다"고 분석했는데,
**명령값 크기만 비교한 잘못된 진단**이었다.

실제 메커니즘: 쓰고 있던 트림(-0.055 ~ -0.067)이 올바른 값(-0.051)보다 **0.004~0.016 더
음수**였고, 그 초과분이 모델의 +0.0115를 **거의 정확히 상쇄**했다. 그 결과 override를 뺀
12개 run 전부에서 다음 패턴이 나왔다:

| run | 모델 raw (좌/우 틱) | 최종 명령 (좌/우 틱) |
|---|---|---|
| 133046 | +0.0096 평균, 좌 78 / 우 0 | -0.0504 평균, 좌 **0** / 우 **78** |
| 132705 | +0.0054 평균, 좌 43 / 우 44 | -0.0446 평균, 좌 **0** / 우 **87** |
| 134456 | +0.0078 평균, 좌 97 / 우 14 | -0.0522 평균, 좌 **0** / 우 **111** |

모델이 좌회전을 내는 틱이 78~99개인데 **최종 명령이 좌회전인 틱은 0개**. 트림을 -0.051로
정확히 맞추면 모델 출력이 그대로 살아난다 → **`--model_angular_gain`은 아마 불필요.**

## 5. override가 모델을 전면 폐기하던 문제

`--route_mode direct` + `--enable_straight_segment_override` 조합에서, 경로가 직선 하나뿐이라
near/far route_bearing이 항상 일치 → **직진 판정이 100% 상시 발동** → 모델 출력이 매 틱
폐기됨. 실측 확인: 주행 틱 100개 전부 `override_reason=straight_segment`, 최종 명령이
**정확히 상수 -0.056**(모델 raw는 +0.0094~+0.0222로 변동).

즉 "모델이 좌측 궤적을 내는데 로봇이 못 따라간다"의 직접 원인. 회전이 필요하면
**`--route_mode osrm`과 함께 써야** 한다(직진 구간엔 자동 발동, 회전 구간엔 자동 해제).

데모용으로 직진을 더 확실히 보장하려면 `--straight_force_zero` 추가(경로 폴리라인의
서브미터 꺾임으로 인한 미세 조향까지 제거, 남는 조향은 트림뿐).

## 6. 인프라 실패 모드 4가지 (별개 문제, 전부 실측)

데모 품질에 직접 영향가므로 기록한다.

### 6-1. SDK 서버가 죽은 브라우저 핸들을 캐싱 → 스스로 복구 불가

`browser_service.py:28` `initialize_browser()`가 `if self.browser: return`으로 시작한다.
브라우저가 크래시해도 `self.browser` 객체는 남아서 **초기화를 건너뛰고 죽은 페이지에 요청을
보낸다 → 영원히 행.** 실측 악화 과정:

| run | 결과 |
|---|---|
| 163757 | 11틱 주행 성공 |
| 163844 | 1틱 후 `send_control_failed` |
| 163933 | 워밍업부터 행 |

**좀비 프로세스만 지워도 복구되지 않는다 — 서버 재시작이 유일한 해결책.**

### 6-2. 좀비 Chrome 누적

Ctrl+C로 배포를 끊을 때마다 헤드리스 Chrome이 정리되지 않고 남는다. 오늘 pyppeteer 28~43개,
chrome 75개까지 누적. 안전한 식별자는 **`--user-data-dir=/home/moai/.local/share/pyppeteer`**
(실행 바이너리는 일반 Chrome과 같은 `/opt/google/chrome/chrome`이라 경로로는 구분 불가).

```bash
pgrep -fc "share/pypp[e]teer"          # 확인 (0이어야 정상)
pkill -f "share/pypp[e]teer"           # 정리 (일반 Chrome 창은 안 건드림)
```

### 6-3. `/sdk` 페이지 로딩이 `networkidle2`를 못 채워 타임아웃

`browser_service.py:59`가 `page.goto(..., {"waitUntil": "networkidle2"})`를 쓴다.
`api.mapbox.com`이 일시적으로 무응답이면 그 요청이 매달려 네트워크가 유휴가 되지 않아
**30초 Navigation Timeout**이 난다. 실측: `api.mapbox.com`이 3초 무응답 → 재시도 시 200.
이 네트워크는 DNS가 `64:ff9b::` NAT64 주소를 반환하므로(IPv6 변환 환경) 간헐적 끊김이 생긴다.

### 6-4. 로봇 오프라인 판별법 (중요)

`/data`가 **HTTP 200을 빠르게 반환해도 로봇이 온라인이라는 뜻이 아니다** — 브라우저에 남은
마지막 수신값을 즉시 반환하기 때문. 반드시 다음을 확인할 것:

```bash
# timestamp가 호출마다 변하는지 + signal_level + 영상
curl -s http://127.0.0.1:8000/data | python3 -c "import json,sys,time; d=json.load(sys.stdin); print('signal',d.get('signal_level'),'지연',round(time.time()-d['timestamp']),'초')"
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8000/v2/front   # 404면 영상 없음
```

로봇 오프라인의 3징후: **`timestamp` 고정 / `signal_level=0` / `/v2/front` 404.**
세션 마지막에 이 상태가 되어 테스트를 완료하지 못했다(소프트웨어 쪽 원인 아님).

  --goal_lat <위도> --goal_lon <경도> \

### 하드웨어 트림 재측정 (모델 완전 배제)

```bash
python3 deployment/pure_teleop_straight_test.py \
  --linear 0.3 --duration 30 --angular_bias -0.051 --enable_angular_dither --skip_gps
```
