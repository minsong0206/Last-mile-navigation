# 실주행 경로 vs 모델 예측 궤적 불일치 분석 (2026-08-25)

대상 로그: `deploy_20260810_223436.jsonl` (2026-08-10 22:34, 서울과학기술대 프론티어관 앞,
OmniVLA-Edge 20m 체크포인트 실배포, 223 tick, 82초 주행)

## 배경

실배포 대시보드/로그를 보고 "로봇 실제 주행 경로가 모델이 낸 예측 trajectory와 완전히
다르게 나온다"는 문제가 제기되어 조사함. 조사 과정에서 시각화 자체의 문제(2건)와 실제
시스템의 문제(3건)가 섞여 있었음이 드러났다 — 아래에 순서대로 정리.

---

## 1. 시각화 자체의 문제 (실제 시스템 버그 아님, 그래프 설계 문제)

### 1-1. heading 추정이 GPS 양자화 잡음에 취약함

ego-centric 패널에서 "실제 경로"를 로봇 좌표계로 회전시키는 데 쓸 heading을 "최근
서로 다른 GPS fix 2개"로 계산했는데, 이 GPS가 **위경도값이 약 0.42m 단위로만 갱신**된다.
그 결과 실제로는 계속 SW쪽(-90~-120°)으로 가는 경로인데도 인접한 두 fix만 비교하면
위도/경도 중 어느 쪽이 먼저 양자화 경계를 넘었는지에 따라 방향이 남(-90°)↔서(180°)로
순간적으로 튀는 구간이 여러 곳 생김.

**해결**: heading을 "최근 두 점"이 아니라 **"누적 이동거리가 1.5m 이상 되는 구간"**으로
추정하도록 변경. 여러 quantization step을 평균화해서 -90°~-128° 사이(실측 전체 평균
-110.8°와 일치)로 안정화됨.

### 1-2. "과거"와 "미래예측"을 원점 기준 앞/뒤로 그려서 항상 반대처럼 보임

처음 설계는 오른쪽 패널에 "최근 지나온 경로(회색, 항상 forward<0=뒤쪽)"와 "모델이
예측한 미래 경로(청록, 항상 forward>0=앞쪽)"를 같이 그렸음. 이러면 **로봇이 예측대로
잘 움직였는지와 무관하게 두 선이 원점에서 위/아래로 항상 반대 방향처럼 보이는 구조적
문제**가 있음 — 과거는 정의상 뒤에 있고 미래 예측은 정의상 앞에 있기 때문.

**해결**: "과거 vs 미래예측" 대신 **"같은 원점·같은 0~2.4초 구간에서, 모델 예측 vs
그 이후 실제로 일어난 일"**을 겹쳐 그리도록 재설계. 이제 두 선 다 forward>0(위) 방향으로
나가며, 벌어지는 정도가 곧 진짜 예측-실제 불일치를 의미함.

## 2. 실제 시스템 문제 (아래 3가지가 겹쳐서 나타남)

### 2-1. 제어 변환 공식 버그 — **확정, 이미 수정됨**

`waypoint_to_control()`이 waypoint까지의 실제 시간(target_step=2 → 0.9초) 대신
**제어 루프 주기 `DT=1/3초`로 나눠서** 속도를 계산하고 있었음. 이 로그의 `linear`/`angular`
218개 tick 전부가 이 옛날 버그 공식과 **소수점까지 정확히 일치**해서, 이 배포 실행이
그 버그를 그대로 안고 돈 것이 100% 확정됨.

- 실제 전송된 angular 명령이 수정 공식 대비 평균 **2.45~2.7배 부풀려짐**
- 안전캡(±0.3rad/s) 포화가 46/218회(21%) 발생 — 수정 공식이었다면 12/218회(5.5%)만
  발생했을 것
- 부호(좌/우 방향) 자체는 218/218 전부 모델 예측과 일치 (뒤집힘 없음)

**수정 커밋**: `988066f` (2026-08-11 09:32, "Fix two real-robot deployment bugs found
in field testing") — `omnivla_edge_deploy.py::waypoint_to_control()`이 이제
`target_time_s = (target_step+1) * CTX_STRIDE_SEC`로 나눔. **다음 실주행부터는 해소된
상태.**

### 2-2. heading 소스가 실제 이동방향과 90~130° 정도 어긋남 — **정황 증거, 미확정**

로그가 진단용으로 남긴 `heading_diff_deg`(IMU컴퍼스 vs GPS궤적) 30개 샘플의 circular
mean이 약 **+97°** (90°에 근접). 같은 날 커밋(`988066f`)에서 다른 브랜치가 시도했다가
"추측으로 상수 넣지 말고 로그로 검증하자"며 되돌린 가설과 정확히 일치하는 크기 —
**컴퍼스 bearing→수학각 변환 시 90도 보정이 빠졌을 가능성**.

- 다만 표준편차 37~65°로 크고, 부호가 반대인 이상치 2개(-164°, -82°) 존재 — GPS
  해상도(아래 2-4) 자체의 노이즈가 섞여있을 가능성 있음
- 이게 맞다면 모델이 받는 지도(heading-up 회전) 자체가 대략 직각 정도 잘못 들어갔다는
  뜻 — CLAUDE.md에 기록된 "배포 시 좌회전 편향" 미해결 이슈의 유력 후보

**해결 방향 (아직 미적용)**: `omnivla_edge_deploy.py`에 `estimate_heading_from_track()`
(GPS 궤적 기반 heading, 진단용으로 이미 구현됨)이 있음. 다음 실주행에서
`heading_diff_deg`가 계속 90°대 근처(고정 오프셋)로 나오면, IMU 컴퍼스 대신 이
GPS궤적 기반 heading을 **실제 제어(지도 생성)에도 전환**하는 것을 검토.

### 2-3. 실제 주행 속도가 모델 예측의 약 30%밖에 안 됨 — **오늘 새로 확정**

GPS(성김)만으로는 판단이 어려워서, 로그에 담긴 **로봇 자체 센서(자이로 z축, 속도)를
dead-reckoning**해서 검증함:

- **단위 검증** (둘 다 GPS와 무관한 방식으로 교차검증):
  - 자이로 z축(gz): 컴퍼스 시작-끝 값 차이(오프셋 버그와 무관한 진짜 회전량, +36.0°)와
    "gz를 deg/s로 보고 전체 82초 적분"한 값(47.4°)이 같은 부호·자릿수로 맞아서
    **deg/s로 확정** (rad/s로 보면 2716°가 나와서 말이 안 됨)
  - speed(로봇 자체 속도 리포트): 평균 1.12, commanded linear 0.3m/s를 km/h로 환산한
    1.08과 근접 → **km/h로 확정**. 이 값을 적분한 총 주행거리(24.8m)가 GPS 순변위
    (직선, 하한선 11.36m)보다 크고 같은 자릿수라 곡선 경로와도 부합
  - (참고) 자이로 서브샘플의 타임스탬프는 tick의 ts와 다른 시계를 써서 **~67.8초의
    고정 오프셋**이 있었음 — median 오프셋으로 보정 후 사용
- **결과**: 217개 tick 전체에서, 2.4초(모델 예측 horizon)당
  - 모델 예측 전진거리 평균 **2.065 m**
  - 실제(dead-reckoned) 전진거리 평균 **0.6 m**
  - 비율(실제/예측) 평균 **0.30**, median **0.315**

즉 **로봇이 모델이 예측한 속도의 약 30%로만 실제 전진**했음. 방향(좌/우) 문제와는
완전히 별개의 **크기(스케일) 불일치**.

**원인 분해 (2026-08-25 추가 확인) — 대부분 안전캡(MAX_V) 때문임이 확인됨**:

| 구간 | 값 | 비율 |
|---|---|---|
| 모델 raw 예측이 내포하는 평균 속도 (8번째 waypoint/2.4s) | 0.861 m/s | — |
| 안전캡 `MAX_V` | 0.300 m/s | **0.861의 34.9%** |
| commanded linear 평균 | 0.297 m/s | MAX_V의 99.1% (거의 항상 캡에 붙어있음) |
| 실제(dead-reckoned) 평균 속도 | 0.250 m/s (=0.6m/2.4s) | commanded의 84% |

`0.349 × 0.84 ≈ 0.293` — 앞서 구한 전체 비율(0.30)과 거의 정확히 일치. 즉 30% 손실의
**대부분(약 65%p)은 `MAX_V=0.3m/s` 안전캡 자체**에서 오고, 나머지(약 16%p)만 "명령 대비
실제 실행 효율"(가속 지연, 회전 중 실제 전진량 감소 등 현실적인 손실)이다. commanded
linear가 MAX_V의 99.1%라는 건 **사실상 거의 매 tick 안전캡에 붙어서 주행했다**는 뜻.

**해결 방안 (우선순위순)**:

1. **`MAX_V`를 단계적으로 올려보는 실험 (가장 저렴, 재학습 불필요)** — 지금 0.3m/s는
   모델이 학습 데이터 기준으로 기대하는 속도(0.861m/s)의 35%밖에 안 됨. 안전이 확보되는
   한도 내에서(예: 0.4~0.5m/s부터) 조금씩 올려보면서 예측-실제 일치도가 개선되는지
   확인하는 게 가장 빠르고 값싼 첫 검증. 코드 한 줄(`MAX_V` 상수) 수정으로 바로 테스트
   가능, 다음 실주행 때 DT버그 수정판과 같이 시도해볼 것.
2. **모델의 속도 가정을 실제 운용 속도에 맞춰 재조정 (근본적 해결, 재학습 필요)** — 만약
   0.3m/s가 안전상 올릴 수 없는 값이라면(보행자 밀집 인도, 저속 필수 등), 반대로
   모델 쪽을 이 속도에 맞게 다시 학습해야 함. rides_11 학습 데이터를 촬영한 로봇의 실제
   주행 속도 분포를 확인해서, FrodoBot Mini의 목표 속도(0.3m/s 근방)와 비슷한 구간만
   골라 쓰거나, `METRIC_WAYPOINT_SPACING`/`WAYPOINT_STRIDE`를 재조정해서 "0.3m/s로
   0.3초 이동 시 실제 거리"에 맞게 정규화 기준을 다시 잡는 방법이 있음. 아래 3장의
   waypoint horizon 확장 작업(어차피 dataset 재추출 필요)과 **같이 진행하는 게 효율적**
   — 두 문제 다 "학습 데이터의 시공간 가정이 FrodoBot Mini의 실제 물리 조건과
   안 맞는다"는 같은 뿌리에서 나옴.
3. **캡에 걸릴 때 각도까지 같이 재조정되는 문제 별도 확인** — `clip_control()`은
   linear가 캡에 걸리면 angular도 비율 유지하며 같이 줄임. commanded linear가 거의 항상
   캡(99.1%)에 붙어있었다는 건 **거의 매 tick 이 재조정 로직이 작동했다**는 뜻이라,
   방향(곡률) 자체도 이 스케일링의 영향을 받았을 가능성이 있음 — 2-1의 DT버그와는
   별개로 추가 점검 가치 있음.

### 2-4. GPS 자체가 성기고 거칢 — 정밀검증의 근본적 한계

- 갱신 간격 평균 **2.3초**, 위경도값이 **~0.42m 단위로만** 변함(양자화)
- 223 tick 중 **71개(32%)는 그 2.4초 예측구간 안에 GPS가 아예 갱신되지 않음**
- 모델 예측 스케일(수십cm)이 이 양자화 단위와 비슷하거나 작아서, GPS만으로는
  tick 단위 정밀 일치/불일치 판정이 불가능함 (전수조사 시 일치율 47.4%로 나왔는데,
  이는 불일치의 증거가 아니라 GPS 잡음끼리 비교한 결과에 가까움)

**해결**: 2-3에서 검증한 dead-reckoning(자이로+속도)을 GPS의 보완재로 사용 — GPS
공백 구간에도 연속적인 근사 궤적을 제공함. 다만 드리프트 누적 가능성이 있어 "정답"이
아니라 GPS와 상호 교차검증하는 용도로 같이 표시함.

## 4. 개선 계획 검증: waypoint horizon(예측 거리)을 더 멀리 보게 하기

**제안된 계획**: map scale 조정 + dataset 재추출 + 재학습을 통해, 지금 3번째
waypoint(~0.9초/0.8m 지점)만 보고 조향하는 것을 더 먼 지점까지 보도록 개선.

**코드로 확인한 현재 상태**:

| waypoint | 시점 | 평균 전진거리 (이 로그 기준) |
|---|---|---|
| 1번째 | +0.3s | 0.28m |
| **3번째 (현재 조향에 씀)** | **+0.9s** | **0.80m** |
| 8번째 (전체 예측의 끝) | +2.4s | 2.07m |

- `deployment/omnivla_edge_deploy.py:250` — `waypoint_to_control(self, pred_xy_m,
  target_step=2)`. 즉 모델은 8개(최대 ~2m/2.4초)를 다 예측하는데 조향은 3번째 하나만 씀.
- `scripts/omnivla/finetune_omnivla_edge.py:101`의 `len_traj_pred: 8`은 **모델
  아키텍처 파라미터**(예측 head 출력 크기)이고, 저자 체크포인트와 `strict=True`로
  architecture가 정확히 일치해야 로드되는 구조. 즉 8개보다 더 먼 waypoint를 진짜로
  예측하게 하려면:
  - `rides11_dataset.py`의 `N_WAYPOINTS`/`FUTURE_MARGIN`을 늘려 **더 먼 미래 GT를 가진
    데이터셋을 다시 뽑아야** 함 (기존 538개 중 미래 프레임이 부족한 segment는 걸러질 수
    있음)
  - 예측 head 크기가 바뀌므로 **재학습 필수**
  - **map scale도 재검토 필요**: CLAUDE.md에 이미 기록된 오프라인 실험 결론이 "현재
    ~2m 예측 horizon 기준으로는 12m 지도가 가장 좋았다"였음. horizon을 늘리면 이 결론이
    유지될지 다시 확인해야 하고, 오히려 지도를 넓혀야(20~25m 쪽) 할 수도 있음

**→ 결론: 제안된 3단계 계획(map scale + dataset + 재학습)이 정확한 접근.** 참고로
target_step 값만 2→7로 바꿔서 이미 예측된 8번째 waypoint(2.07m)를 쓰는 건 재학습 없이
코드 한 줄로 당장 가능하지만, 그 이상(3~5m 등) 진짜로 더 멀리 보게 하려면 위 3단계가
필요함.

**단, 별도로 챙길 것**: 2-3의 속도 스케일 문제를 먼저(또는 같이) 손보지 않으면, 더 먼
waypoint를 보게 해도 "그 지점에 2.4초 뒤 도착한다"는 모델의 시간 가정과 로봇의 실제
도착 시간(훨씬 늦음, 지금은 예측의 30%) 차이가 오히려 더 벌어질 수 있음. 4장의 재학습
작업과 2-3의 속도 재조정을 같이 진행하는 것을 권장.

## 종합 결론

"실주행 경로가 모델 예측과 완전히 다르다"는 인상은 다음이 겹친 결과로 보인다:

1. (확정, 수정됨) 제어변환 버그로 명령 크기가 2.5~2.7배 부풀려지고 안전캡에 자주 걸림
2. (정황 증거) heading 소스가 90~130° 정도 어긋나 지도 입력이 잘못 정렬됐을 가능성
3. (확정) 실제 속도가 예측의 30%밖에 안 됨 — 별개의 스케일 문제
4. (한계) GPS 해상도가 낮아서 세밀한 검증 자체가 어려움 → dead-reckoning으로 보완

**"완전히 반대 방향"이라는 표현은 과장** — 부호(좌/우) 자체가 뒤집힌 사례는 없었고
(제어변환 버그: 218/218 부호 유지), 확인된 각도 차이도 45~130° 수준이지 180°(정반대)는
아니었다.
