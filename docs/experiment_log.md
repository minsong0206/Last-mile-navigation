# 좌편향(left-turn bias) 조사 — 공유 실험 로그

**이 문서의 목적**: Harness 1(학습/모델 분석, 오프라인)과 Harness 2(실배포 디버깅,
실시간)가 서로 다른 터미널의 독립된 Claude Code 세션으로 동시에 작업할 때 쓰는
단일 진실 공급원. 새 가설을 세우거나 실험을 시작하기 전에 **반드시 이 문서부터
읽고**, 이미 확인된 걸 다시 하지 말 것. 실험을 하나 끝내면 성공/실패/blocked
가리지 않고 이 문서에 결과를 추가할 것.

마지막 갱신: 2026-10-03

**세션 종료 시점 상태(2026-10-03 저녁, 로봇 배터리 방전으로 중단)**: §1-8/§3-1의
근거로 near-goal override(`--near_goal_override_dist_m`, 기본 8.0m)와 heading

### 1-4. map_range_m(맵 스케일) 분리 실험 — **강한 양성 결과, §1-3 보류 후 대체 작업**

**배경**: §1-3(데이터 자체의 goal-근접 skew 체크)이 "ms" 머신 접근 문제로 보류됨
(사용자 확인, 2026-10-03). CLAUDE.md의 또 다른 유력 후보 "맵 스케일(25-27m)이 실제

**방법** (`deployment/analysis/map_scale_isolation_test.py`, 신규 작성 — production
코드 그대로 재사용, 로봇/deployment/*.py 수정 없음): §1-2와 같은 run
(`deploy_20260926_132829.jsonl`, 27m 체크포인트, `heading_mode=route_aligned_fixed`)
에서 좌편향이 가장 강했던 두 버킷(5-10m, 10-15m)의 real tick을 그대로 가져와서,
**실제 GPS 위치/heading/past_track/카메라 프레임은 전부 고정**하고 **`map_range_m`만
27m(원본)→15m→10m→5m으로 줄여서** 같은 `LiveMapBuilder`/같은 route/같은 canvas로
지도만 다시 렌더링해 추론. (canvas는 zoom에만 의존하고 map_range_m과 무관해서 여러
`LiveMapBuilder` 인스턴스가 공유 가능 — 네트워크 재요청 없음.) 실제 goal까지의
거리는 전혀 안 바뀜 — "진짜 가깝다"는 사실과 "지도가 얼마나 넓게 그려지는가"를
분리하는 게 목적.

**결과** (angular: 양수=좌, 음수=우):

| bucket | n | 27m(원본) | 15m | 10m | 5m |
|---|---|---|---|---|---|
| 5-10m  | 35 | **+0.0364** (std=0.0165, **35/35 좌**) | -0.0006 (18/35 좌) | +0.0033 (26/35 좌) | -0.0047 (13/35 좌) |

**해석**:
- 27m(학습 스케일 그대로)에서는 두 버킷 **전부 100%/100% 결정론적으로 좌회전** —
  입력이 뭐든 상관없이 좌회전만 나온다는 §1-2 결론과 일치, std도 매우 작음(0.003-0.017)
  → "확고한 학습된 prior".
  - **지도를 15m로만 줄여도 이 결정론적 패턴이 즉시 깨짐** (좌/우 비율이 거의
    50:50 또는 섞인 비율로 바뀌고, 평균도 거의 0으로 붕괴). 10m/5m에서도 27m 같은
    강한 좌편향은 재현되지 않음(5m에서는 5-10m 버킷이 오히려 평균 우회전으로 뒤집힘).
  - **실제 GPS상 goal까지의 거리는 세 조건에서 완전히 동일** — 바뀐 건 렌더링
    스케일뿐. 따라서 "goal에 실제로 가깝다"는 사실 자체가 아니라 **"그 거리를
    27m짜리 넓은 지도에 그렸을 때 생기는 무언가"가 좌편향의 직접 원인**이라는

  문제가 좌편향의 유일한 원인"이라고 완전히 확정하진 못함 — 데이터 클래스

### 1-8. 근본 메커니즘 직접 규명 — "future route의 화면상 픽셀 길이"가 진짜 변수였음 (가장 중요한 발견)

**계기**: 사용자가 "주행기록 보고 진짜로 분석해봐"라고 요청 — 지금까지 §1-4/1-6/1-7은
전부 angular 평균/결정론 비율 같은 **집계 통계**만 봤음. 이번엔 실제 저장된
map_replay_path PNG(`deployment/logs/frames/<run_id>/map_*.png`)를 직접 눈으로
보고, 빨간 future-route 선의 **픽셀 단위 bbox**를 측정해서 비교함.

**방법**: `deploy_20260926_132829.jsonl`(route_aligned_fixed, 27m)의 저장된
map PNG 233장 중 aligned_ticks 177장 전부에서 빨간 픽셀(R>150,G<100,B<100) bbox를
OpenCV 없이 numpy로 직접 측정(`bbox_h`=세로, `bbox_w`=가로, 기록된 `angular`와
`dist_to_goal_m`에 매칭). 같은 걸 오늘 실외 실주행 2개(`20261003_134319`,
`20261003_135403`, 둘 다 `auto` 모드, 진짜 꺾이는 경로, GPS 노이즈 포함)에도
적용해서 교차검증. 추가로 같은 real tick들을 12m/20m(§1-6/1-7) 구세대 렌더링으로
다시 그려서 bbox_h가 어떻게 바뀌는지도 측정.

**핵심 발견 1 — `132829`(완전 직선 경로)에서 `bbox_w`(가로, 즉 실제 곡률)가
처음부터 끝까지 **단 한 번도 6px에서 안 변함** (177개 tick 전부 동일)**:
이 경로는 25m부터 6m까지 내려오는 전 구간이 **진짜로 완벽한 직선**이고(GPS 오차
수준의 흔들림조차 없음), 모델이 "읽을 곡률 정보" 자체가 애초에 존재하지 않았음.
반면 `bbox_h`(세로, 화면에 보이는 future-route의 길이)는 139px(25m)→77px(15m)→
27px(7.5m)→15px(6m)로 **매끄럽게 줄어들고, angular는 거의 정확히 이 bbox_h 감소와
반비례해서 커짐**(bbox_h≥100px: |angular|<0.01 근처 진동, bbox_h 40-60px:
+0.012~0.018로 상승 시작, bbox_h 25-40px: +0.02~0.05, bbox_h<21px: +0.034~0.063로
가장 강하고 일관됨). **즉, "실제 goal까지의 거리"가 아니라 "화면에 그려진
future-route 선분의 픽셀 길이(bbox_h)"가 좌편향의 진짜 설명변수였음** — 곡률
내용은 시작부터 끝까지 0이었으므로 "곡률이 압축돼서 안 보인다"가 아니라
**"짧은 선분 자체가 트리거"**라는 더 구체적인 메커니즘.

**핵심 발견 2 — map_range_m을 줄이면 같은 real tick에서 bbox_h가 커짐(§1-4/1-6/1-7이
왜 효과 있었는지 이제 수식으로 설명됨)**: 같은 tick(예: tick219, 실제 6.0m)을
27m/20m/12m으로 각각 렌더링하면 bbox_h = 15px → 20px → 34px로 늘어남(tick202,
7.5m: 24px→32px→54px). **"맵을 좁히면 좌편향이 약해진다"는 §1-4/1-6/1-7의 결과는
"곡률을 더 잘 보여줘서"가 아니라, 같은 실제 거리를 더 좁은 지도에 그리면 그 거리가
화면상 더 "길어 보여서"(=bbox_h가 더 커져서) "짧은 선분" 트리거 영역을 아직 안
밟기 때문**이었음 — §1-6/1-7에서 12m/20m이 27m의 근거리 100% 결정론을 재현하지
못한 이유가 정확히 이것으로 설명됨(같은 6-7.5m인데 12m 지도에서는 bbox_h가
34-54px로 "안전 구간"에 있음).

**핵심 발견 3 — 오늘 실제 `auto` 모드 주행(진짜 꺾이는 경로, GPS 노이즈 포함)에서도
같은 bbox_h 임계값이 재현됨**(`20261003_134319`, 231 LIVE tick, bbox_h로 재버킷):

| bbox_h(px) | n | mean angular | n_left:n_right |
|---|---|---|---|
| 100+ | 75 | +0.0063 | 49:26 |
| 60-100 | 27 | +0.0055 | 13:14 |
| 40-60 | 51 | **-0.0167** | 12:39 (실제 우회전 구간 — 정상 반영) |

이 run은 사용자가 "직진 후 우회전"이라고 명시한 **진짜 우회전 경로**라서 중간
구간(25-60px)은 모델이 실제 우회전을 올바르게 반영(-0.08, -0.02) — 즉 bbox_h가
크거나 중간일 때는 모델이 **실제 지도 내용을 정상적으로 읽는다**는 뜻. 그런데
**bbox_h<25px로 떨어지는 순간(=§2-1에서 이미 "5-10m/<5m 버킷"으로 기록했던 구간과

실제로 접근 못 함) bbox_h가 작아지는 이유가 "진짜 근접"이 아니라 "경로가 heading
축에서 벗어나 화면 밖으로 꺾여서"인 경우와 섞여 있어 이 run 단독으로는 깨끗한
확증 사례로 못 씀 — 거리 자체가 안 줄어든 상태에서 bbox_h<40 구간은 실제

**종합 — 지금까지 중 가장 구체적이고 실행 가능한 그림**:
1. 모델은 future-route 선분이 화면상 **대략 bbox_h≥40-60px(27m 체크포인트 기준,
   실측 dist로는 대략 10-12m 이상) 이상일 때는 지도 내용을 정상적으로 읽고
   반영**함 (실제 우회전/직진을 맞게 반영 — 134319의 40-60px 구간, §1-2의 20m+
   버킷에서 지도 반전 시 부호도 반전하는 것과 일치).
2. **bbox_h가 대략 25px 미만(27m 체크포인트 기준, 실측 dist로는 대략 7-8m 이내)로
   떨어지면, 실제 지도 내용(곡률 유무·방향)과 완전히 무관하게 좌회전으로
   수렴**함 — 이건 "곡률 압축" 문제가 아니라, **"짧은 future-route 선분"이라는
   화면 구성 자체가 OOD 트리거**로 작동하는 것으로 보임. 가장 그럴듯한 원인:
   학습 데이터의 세그먼트가 "goal 근처"에서 끝나도록 잘려 있고
   (`episode_selector.py`의 세그먼트 분할 방식상 자연스러움), 그 "세그먼트 끝 =
   future-route 선분이 짧아 보이는" 시점들이 데이터에서 우연히 좌회전 쪽으로
   쏠려 있었을 가능성 — 이건 결국 **§1-3(아직 blocked)이 풀려야 완전히 확정**됨.
   하지만 이제는 "막연히 데이터 불균형일 수도"가 아니라, **"정확히 어떤 화면
   구성(짧은 red 선분)에서 트리거되는지"까지 구체적으로 좁혀짐**.
3. **즉시 배포 가능한 완화책(재학습 불필요)**: 현재 `dist_to_goal_m`이 이미 매
   tick 계산되고 있으므로, "future-route가 화면상 짧아지는 거리"를 체크포인트별로
   역산해서(27m 체크포인트는 대략 7-8m, 이 분석의 bbox_h<25px 임계값을
   `6.15px/m`로 환산) **그 거리 이내에서는 모델의 raw angular를 믿지 않고, 이미
   코드에 있는 `route_bearing_rad()`(GPS 궤적 기반 목표 방향) 쪽으로 전환하거나
   angular를 강하게 dampen하는 안전장치**를 넣는 게 당장 적용 가능한 가장
   실용적인 수정으로 보임. §3에 제안으로 추가함.
4. 재학습 방향(§1-4/1-6/1-7, 12m/20m/현재 신세대 geometry로 더 작은
   map_range_m 재학습)은 여전히 맞는 방향이지만, 이걸로 설명되는 건 "같은 실제
   거리에서 bbox_h가 더 커져서 트리거 구간에 늦게 도달한다"는 것뿐 — **트리거
   자체(짧은 선분→좌회전)가 데이터에서 온 거라면, 맵을 아무리 줄여도 로봇이
   실제 목표에 충분히 가까워지면(각 스케일에서 자기 bbox_h<25px 상당 구간) 결국
   다시 나타날 수 있음**. 완화책 3과 재학습 방향을 **같이** 가는 게 안전함.

**다음에 할 일**: (a) §3에 적은 완화책을 Harness 2가 검토, (b) §1-3(Arrow 접근)이
풀리면 "세그먼트 끝 근처 GT heading의 좌/우 쏠림"을 직접 확인해서 위 2번 가설을

- GPS가 멈추기 직전 `gps_track` 추정값이 `-90.0°`(양자화 격자각도)에서 고정되고,
  `route_bearing`은 그 위치 기준 `-162.0°`(실제 경로가 요구하는 진짜 우회전 방향,
  멈춘 위치에서는 그대로 고정)로 유지 — 72° 차이가 `heading_anchor_pull_threshold_deg`
  (20°)를 영구히 초과해서 `map_heading_source="gps_track_pull"`로 전환된 뒤
  **다시는 안 풀림**(tick165~219 내내 `gps_track_pull` 고정).
- 결과: 지도가 `-90°`로 고정 렌더링된 채 모델이 (§1-8/1-9/1-10에서 이미 확인한
  대로 지도 내용에 충실하게) 계속 강한 우회전(`angular` -0.11~-0.21)을 명령 —
  그런데 GPS가 안 바뀌니 "충분히 돌았다"는 피드백이 전혀 없어서 **끝까지 우회전만
  반복**. 사용자가 보고한 증상과 정확히 일치.

**근본 원인(새로운 버그, §1-9/1-10의 "GPS noise→heading 왜곡"과는 다른 레이어)**:
기존 `route_corrected`(§1-9/1-10 당시 구조)는 "오래 어긋나면 **route_bearing**(안정적
쪽)으로 되돌린다"였는데, `route_bearing_anchored`는 의도적으로 방향을 반대로
설계함("오래 어긋나면 **gps_track**을 믿는다", §1-11 참고 — Harness 1이 제안한
설계 자체). **"지속적으로 어긋남"만으로 신뢰를 넘기는 판정 기준이, "진짜 움직여서
반박하는 것"과 "GPS가 멈춰서 생기는 가짜 반박"을 구분 못 함** — frozen GPS는
`gps_track` 추정치 자체가 다시는 안 바뀌므로 "지속 반박"처럼 보이는 조건을 영원히
만족시켜버림. 설계 자체(지도 heading 안정화 vs 이탈 감지 분리)는 맞는 방향이었지만,
**pull 조건에 "실제로 GPS가 최근에 움직였는가"(freshness) 체크가 빠져있던 게
직접적인 버그**로 확정.

**좌편향(B) 관련**: 사용자가 "좌편향도 여전함"이라고 보고했는데, 이 run의 정상
구간(tick34-130, `route_bearing_anchor` 소스, dist 16-20m)에서 angular는 +0.01~+0.03
수준 — §1-2/1-9에서 이 거리대에 이미 측정했던 작은 잔차 좌편향과 일치하는 크기라,
**새로운 악화가 아니라 기존에 이미 특정된(§1-3 blocked) 잔차가 그대로 재확인된
것**으로 보임(이 run은 `near_goal_override_dist_m=0`으로 B의 주 완화책도 꺼둔
상태였다는 점 고려).

**제안(코드는 안 건드림, Harness 2 검토용)**: pull 조건에 freshness 체크 추가 필요
— 예: 직전 `heading_anchor_pull_persist_ticks`개 tick 동안 `gps_accumulated_path_m`
또는 `gps_net_displacement_m`가 일정량(예: MIN_NET_DISP_M 수준) 이상 **실제로
증가했는지**도 같이 확인하고, 증가가 없으면(=GPS 프리징 중) pull 자체를 보류하고
기존 anchor(route_bearing) 유지. 더 근본적으로는, 이 freezing 문제가 heading_mode와
무관하게 반복적으로 실패를 일으키고 있어서(§2-1, §1-9, 이번 §1-12까지 3번째) —
GPS 프리징 자체를 감지해서(예: N틱 연속 `gps_accumulated_path_m` 무변화인데
`speed`>0이면) 별도로 로그/알림하는 진단 장치를 추가하는 것도 고려할 만함.

### 1-13. §1-12 수정 구현 완료: GPS 동결 감지 안전장치 추가 + `route_bearing_anchored`의 pull 버그 수정

Harness 1의 제안(위 §1-12 제안)과 사용자가 직접 선택한 "GPS 동결 감지 안전장치"를
**같은 감지기 하나로** 구현해서 두 문제를 동시에 고침:

- **감지 로직**(`past_track`과 독립적으로 추적 — 정렬확인/route_corrected가
  `past_track`을 clear해도 끊기지 않음): 위치가 `gps_freeze_min_disp_m`(기본
  0.03m) 이상 못 움직인 채 `gps_freeze_persist_ticks`(기본 10틱, ~3.3초)
  이상 지속되고, 그동안 `frodobot_raw.speed`가 `gps_freeze_speed_threshold_mps`
  (기본 0.15m/s) 이상이면(=움직이고 있다고 자기보고하는데 위치만 안 바뀜)
  `gps_frozen=True`로 판정.
- **용도 1 (사용자가 선택한 안전장치)**: override 체인 최우선 순위(off_route_safety/
  near_goal/straight_segment보다 위)로 추가 — `gps_frozen`이면 무조건
  `linear=angular=0.0`, `override_reason="gps_freeze_safety"`. 위치 입력 자체가
  신뢰 불가능하면 나머지 override들의 거리/route_bearing 계산도 같이 못 믿기 때문에
  가장 먼저 걸림.
- **용도 2 (Harness 1의 pull 버그 직접 수정)**: `route_bearing_anchored`의 pull
  조건에 `and not self._gps_frozen_now` 가드 추가 — 동결 중에는 아무리
  `heading_anchor_pull_ticks`가 임계값을 넘어도 `gps_track_pull`로 전환되지 않고
  `route_bearing_anchor`를 유지(§1-12에서 확정된 버그를 해당 틱 자체가 아예 못
  일어나게 원천 차단).
- 다른 2026-10-04 신규 메커니즘들과 달리 **이건 순수 안전장치라 트레이드오프가
  없어서 기본 ON**(옵트아웃 방식, `--disable_gps_freeze_guard`로만 끌 수 있음) —
  `near_goal_override_dist_m`(기본 8.0, 0으로 끄는 방식)과 동일한 선례를 따름.
- 대시보드(`debug_web.py`)에도 `gps_frozen` 행과 `override_reason=gps_freeze_safety`
  라벨(`🛑 GPS 동결 안전장치`) 추가.
- **검증**: `deployment/offline_smoke_test.py`에 `test_i_gps_freeze_guard` 추가 —
  §1-12 실측 패턴을 합성 재현(실제 이동 15틱 → speed>0인데 위치 동결 15틱),
  `heading_anchor_pull_threshold_deg=0`/`persist_ticks=1`(가드 없으면 즉시 pull될
  가장 불리한 조건)에서도 동결 구간 내내 `gps_track_pull`로 전환 안 되는 것과
  `override_reason=gps_freeze_safety`/명령 (0,0) 고정을 직접 확인. 기존 7개 + 신규

- **⚠ 아직 실기기 미검증** — 다음 실주행에서 §1-12와 동일한 장소/상황(또는 GPS

### 1-16. `deploy_20261004_133317.jsonl` 분석 — "이전 두 실험보다 심해짐" 원인 2건 확정 + 수정 완료

**사용자 보고**: 직진구간 좌회전이 이전 두 실험보다 심해짐, 우회전을 제대로 못하고

**원인 1 — `gps_track` **heading 추정값 자체**가 양자화 격자각도에 고정되는
새 변종(위치는 멈추지 않음, §1-13의 위치-동결과는 다른 메커니즘)**: tick117~126에서
`route_bearing`이 `-105.6°→-119.8°→-139.5°`로 **진짜 급우회전**(최종 +178.6°까지,
거의 180도 전환)을 요구하는 지점에 진입. 정확히 그 순간 `gps_heading_rad`가

있음. §1-2/§1-5가 **`route_aligned_fixed`만 썼던 이유**(GPS 노이즈에 영향 안
받음)가 왜 중요했는지 다시 확인됨. **다음 실외 테스트 전에 GPS 수신 환경(개활지

## 3. Harness 1 제안함 (Harness 2가 검토/반영)

### 3-1. "future-route 선분이 짧을 때 raw angular 불신" 안전장치 (§1-8 근거, 2026-10-03)

**문제**: §1-8에서 직접 확인 — future-route가 화면상 bbox_h<~25px(27m 체크포인트
기준, 실측 dist로 대략 7-8m 이내)로 짧아지면, 실제 지도 내용(곡률 유무/방향)과
무관하게 모델이 결정론적으로 좌회전함. 데이터 불균형(§1-3, 아직 blocked)이
근본원인일 가능성이 높지만, 그거와 별개로 **지금 당장 재학습 없이 배포 코드에서
완화 가능**해 보임.

**제안(구체적 구현은 Harness 2가 판단)**:
- `omnivla_edge_deploy.py`에 이미 있는 `dist_to_goal_m`과 `route_bearing_rad()`를
  활용 — `dist_to_goal_m`이 체크포인트별 임계값(27m 체크포인트는 대략 7-8m,
  다른 map_range_m이면 `threshold_px/(MAP_SIZE_PX/(map_range_m*(1+REAR_RATIO)))`
  로 환산) 이하로 떨어지면:
  - (a) 가장 단순: raw 모델 angular를 `route_bearing_rad()` 기반 "목표를 향한
    직접 방향"과 가중평균(거리가 가까워질수록 route_bearing 쪽 가중치↑)해서 blend,
    또는
  - (b) 더 단순: 그 구간에서는 raw angular를 그대로 쓰지 않고 route_bearing 기반
    계산으로 완전히 대체.
- 임계값은 체크포인트/map_range_m마다 다름 — §1-8에 측정된 bbox_h↔px/m 환산표
  참고해서 실제 배포 체크포인트 기준으로 재보정 필요.
- **주의**: 이 완화책은 "증상 억제"이고 데이터 불균형이 진짜 원인이면 §1-3이
  풀려야 근본 수정 가능 — 재학습 방향(12m/20m 등)과 병행 권장, 이것만으로
  끝내지 말 것(§1-8 "종합" 4번 참고).
