# 2026-09-26: MAP_NAV → SEMANTIC_NAV 통합 + 실외 필드 테스트에서 발견된 이슈들

이 문서는 세션이 중간에 끊겨도 다음 세션이 바로 이어갈 수 있도록, 오늘 논의된 배경·설계·
구현·테스트·실제 필드 테스트 결과·미해결 이슈를 순서대로 남긴다. 코드 변경은 전부
`Last-mile-navigation_merge/deployment/`(`omnivla_edge_deploy.py`, `debug_web.py`,
`offline_smoke_test.py`) 안에서만 이루어졌고, `forodobot_semantic_nav`는 한 줄도 수정하지
않았다(import만 함).

## 0. 배경

두 저장소가 `unity/` 아래 나란히 있다:
- `Last-mile-navigation_merge` — GPS/OSRM 기반 map navigation. **메인 배포 프로그램**으로 유지.
- `forodobot_semantic_nav` — 카메라 + language instruction 기반 semantic navigation
  (OmniVLA-edge, CLIP text encoder, modality_id=7 "언어만").

목표: 목적지에 거리상 가까워지면 map 기반 주행을 멈추고, 그 지점부터는 semantic 모델이
카메라와 자연어 지시("the red chair" 같은 짧은 명사구)만으로 마지막 접근을 하도록 하는
단일 파이프라인을 만드는 것. **로봇에 명령을 보낼 수 있는 코드 경로는 항상 하나
(`send_control()` 한 곳)만 유지**해야 한다는 게 핵심 제약이었다.

## 1. 아키텍처 분석 (구현 전 조사만 한 라운드)

- `Last-mile-navigation_merge`: `deployment/omnivla_edge_deploy.py::OmniVLAEdgeDeployment` 가
  메인 루프. GPS/IMU(`poll_frodobot()`) → OSRM 경로(`build_live_map.py::LiveMapBuilder`) →
  `OmniVLA_edge_odom`(map-only 모달리티) → `waypoint_to_control()`/`clip_control()` →
  `send_control()`. `debug_web.py`가 대시보드(포트 8080). 로봇 SDK는 `http://127.0.0.1:8000`
  (REST, `/v2/front`, `/data`, `/control`)로 통신 — 이 서버의 실체가 사실 `forodobot_semantic_nav`
  의 `main.py`(FastAPI, hypercorn)였다는 걸 이번에 확인함.
- `forodobot_semantic_nav`: `main.py`+`browser_service.py`가 진짜 SDK 서버(Playwright 헤드리스
  브라우저로 Agora RTC/RTM 세션 소유). `policy/omnivla_policy.py::OmniVLAEdgePolicy`가 모델
  래퍼(`predict_waypoints(context_frames, prompt=None, goal_pose=None, goal_image=None)`),
  `policy/control.py`가 `waypoint_to_velocity()`/`to_control_command()`(순수 함수, 원본 그대로
  재사용). `policy/run_autonomy.py`(별도 프로세스, `AutonomyLoop`)는 **사용하지 않기로 결정**
  — 두 프로세스가 각자 `/control`을 두드리는 구조를 피하기 위해, `OmniVLAEdgePolicy`와
  `policy/control.py`만 라이브러리로 import.
- **language instruction 형식 확인**: `forodobot_semantic_nav/README.md`에 "짧은 영어 명사구"
  (`"blue trash bin"`, `"the red door"`)로 학습됐다고 명시. `"go to the red chair"`처럼 동사가
  들어간 명령형 문장은 **비권장**(CLIP이 문장 전체를 벡터 하나로 인코딩해서 단계별 지시를
  해석 못 하고, 학습 분포도 벗어남) — CLI `--semantic_prompt` help에 명시해둠.

## 2. 설계 및 구현: `nav_mode` 상태머신

```
MAP_NAV
   │ dist_to_goal_m <= semantic_switch_distance_m  (래치, 1회만 — nav_mode 자체가 래치)
   ↓
STOPPING (semantic_stop_ticks만큼 (0,0) 유지)
   ↓
SEMANTIC_INIT ──(초기화 실패)──→ SEMANTIC_ERROR (영구 정지, MAP_NAV로 절대 안 돌아감)
   │ 성공
   ↓
SEMANTIC_NAV ──(inference 실패)──→ SEMANTIC_ERROR (영구 정지)
```

- `DEFAULT_SEMANTIC_SWITCH_DISTANCE_M = 8.0` — **임시 테스트값**, 반복 배포 테스트로 확정할
  예정이라고 계속 유지 중. 오늘 실제로는 `1.0` → `3.0`으로 여러 번 바꿔가며 테스트함.
- `_set_nav_mode()` 한 곳에서만 전이 발생 → 콘솔(`[NAV] ...`)/대시보드 로그/JSONL
  (`event: "nav_mode_transition"`, `dist_to_goal_m`/`threshold`/`prev_nav_mode`/`new_nav_mode`/
  `control_stage` 포함) 세 곳에 동시 기록.
- `_semantic_init()`: `sys.path`에 `forodobot_semantic_nav` 추가(하드코딩된 홈 경로 없이
  `REPO_ROOT.parent / "forodobot_semantic_nav"`로 자동 계산, `--semantic_repo_path`로 override
  가능) → `policy.omnivla_policy`/`policy.control` 지연 import → `OmniVLAEdgePolicy` 로드
  (기본 체크포인트: `forodobot_semantic_nav/best.pth`, 저장소 루트에 실제 존재 확인함) →
  `load_calibration()` 확인(현재 `calibration.json` **없음** → placeholder
  `max_lin_mps=max_ang_rps=1.0` 사용, 경고 로그 남김) → `encode_text(prompt)` warm-up(기존
  `OmniVLAEdgePolicy._text_cache` dict 그대로 재사용, 별도 캐싱 레이어 안 만듦) → 6-frame
  원본 PIL `deque` 준비(MAP_NAV의 텐서 buffer와 완전 분리).
- `_semantic_step()`: 매 틱 `predict_waypoints()` → `waypoint_to_velocity()` →
  `to_control_command()`(전부 `forodobot_semantic_nav` 원본 함수 재사용, 복사/재작성 없음) →
  `(linear, angular)` 반환만 함(전송은 안 함). 대시보드 궤적은
  `waypoints[:,:2] * METRIC_WAYPOINT_SPACING(0.1, semantic 쪽 상수)` → `state.pred_xy_m` —
  MAP_NAV와 좌표 정의(ego frame, x=forward/y=left)가 동일함을 두 저장소 docstring으로 확인한
  뒤 그대로 사용(축 swap/부호 반전 없음).
- **Single control gate 유지**: `run()`의 전송 게이트 한 곳만 수정 —
  `nav_mode_active = self.nav_mode in ("MAP_NAV", "SEMANTIC_NAV")`. `forodobot_semantic_nav/
  policy/run_autonomy.py`나 `RoverClient.control()`은 어디서도 호출하지 않음 — 실제
  `/control` POST는 여전히 `send_control()` 한 곳뿐.

## 3. 발견 및 수정한 버그: 단일 게이트가 SEMANTIC_NAV를 막고 있었음

`nav_mode_active`를 처음 넣을 때(SEMANTIC_NAV가 아직 스텁이던 시점)는
`self.nav_mode == "MAP_NAV"`로만 썼는데, 나중에 SEMANTIC_NAV를 실제로 연동하면서 이 조건을
업데이트하는 걸 빠뜨렸다. 그 결과 실제 LIVE 필드 테스트(`deploy_20260926_165850.jsonl`)에서
SEMANTIC_NAV가 `linear=0.3` 등 유효한 명령을 계속 계산하고 있었는데도 **실제 전송은 계속
(0,0)** 이었다 — 즉 그 구간 동안 로봇이 전혀 안 움직였을 것. `nav_mode_active`를
`self.nav_mode in ("MAP_NAV", "SEMANTIC_NAV")`로 수정하고, 이 정확한 회귀를 잡는 테스트
(`test_k_semantic_nav_sends_nonzero_when_live`)를 추가해서 재발 방지함. 수정 후 실제로
`[SEMANTIC_NAV] [LIVE] linear=+0.28 angular=-0.30`처럼 전송되는 것도 로그로 확인함.

## 4. 실제 필드 테스트에서 나온 이슈들 (일부는 확인만 하고 아직 미해결)

### 4.1 좌회전(좌편향) — 코드 버그 아님, 기존에 이미 알려진 모델 자체 편향

`deploy_20260926_173253.jsonl` 분석: `--heading_mode route_aligned_fixed`라 heading이 route
bearing과 사실상 정확히 일치(`heading_route_diff_deg≈0`)한 상태에서도, 모델이 예측한
`target_waypoint_xy`의 `y`(좌측 성분)가 대부분 양수(평균 +0.19m, 각도로 +7.8°) — **모델
자체가 실제 경로 방향과 무관하게 좌측으로 치우친 궤적을 예측**하고 있음을 확인. 코드에
"-0.05" 같은 하드코딩 보정값은 어디에도 없음(grep으로 model/controller/map builder 전부
확인). 이건 `CLAUDE.md` "알려진 이슈"에 이미 2026-08-10부터 기록된 미해결 문제와 같은 증상
(직진/좌/우 클래스 데이터 불균형 추정) — 이번 재확인은 heading 소스 불일치 가설을 오히려
약화시킴(route_aligned_fixed로 heading을 route에 강제로 맞춰도 편향이 그대로 나옴).

**대응(임시, config로만)**: 근본 수정(재학습/리밸런싱)은 별개로 필요하다고 판단, 대신
빠르게 실험할 수 있도록 두 가지 CLI 옵션 추가:
- `--map_angular_bias_rad_s` (기본 0.0): 모델이 계산한 angular에 이 값을 더함(부분 보정).
  고정 상수라 회전 각도에 비례하지 않으므로 **직진 구간 테스트 전용**이라고 명시.
- `--map_angular_override_rad_s` (기본 None): 지정하면 모델의 angular 예측을 완전히 무시하고
  이 값(보통 0.0)으로 강제 대체. bias보다 우선. "일단 직진만 나오는지" 순수 테스트용.
- 둘 다 JSONL(`angular_before_bias`, `map_angular_bias_rad_s`, `map_angular_override_rad_s`)에
  매 틱 기록해서 보정 전/후를 바로 비교 가능하게 함.
- ⚠ 사용자 본인이 지적한 트레이드오프: 회전이 필요한 실제 구간에서 상수 보정을 켜두면
  좌회전 구간에서 회전량 부족, 세션마다 편향 크기가 다름(8월 +0.0875 vs 이번 +0.03 rad/s
  평균) — **직진 구간 테스트에서만 쓸 것으로 범위를 명확히 좁힘.**

### 4.2 GPS 목표 도달 시 정지 로직이 SEMANTIC_NAV에도 그대로 적용됨 (확인만 함, 미수정)

`_goal_reached`(GPS 기반, `--goal_lat`/`--goal_lon` 대상) 래치가 `nav_mode` 분기 이전에
매 틱 무조건 계산되고, `run()`의 게이트도 `not self._goal_reached`를 요구함 — 즉
**semantic이 "green box"를 향해 주행 중이어도, GPS 좌표가 원래 목표에 가까워지면 멈춘다.**
semantic 쪽엔 비전 기반 도착 감지가 아예 없음(forodobot_semantic_nav 자체에 없는 기능).
사용자가 "코드 수정 말고 확인만"이라고 해서 원인만 짚어두고 수정은 안 함 — 다음 세션에서
필요하면 SEMANTIC_NAV 중엔 이 latch를 건너뛰도록 고칠 것.

### 4.3 GPS 프리징 → semantic 전환이 안 일어난 이유

`deploy_20260926_175131.jsonl`: `dist_to_goal_m`이 `semantic_switch_distance_m=3.0`을 한
번도 못 넘겼음(최솟값 3.9999m). 원인은 tick 80부터 끝까지(~27초) `lat/lon`이 완전히 동일한
값으로 고정된 것 — 그런데 같은 구간에서 `speed`(로봇 자체 리포트)는 계속 1.0~1.3, GPS
timestamp도 정상 증가, `fix_quality`는 계속 1(SPS, DGPS 아님). **GPS 수신기가 실제 위치
갱신 없이 마지막 좌표를 반복 리포트하는 것으로 추정.** 게다가 그 직전에 크래시난 런
(`deploy_20260926_174818.jsonl`)의 마지막 좌표와 **정확히 동일** — 같은 물리적 지점에서
위성 신호가 약해지는 것으로 보이며, 우리 스크립트를 재시작해도 SDK 서버(로봇 연결을 들고
있는 별도 프로세스)는 그대로라 안 풀렸을 가능성. → **결론: threshold(2m/3m) 튜닝 문제가
아니라 GPS 신뢰도 문제** — 개활지 이동 또는 SDK 서버 재시작으로 fix_quality가
2(DGPS)로 올라오는지 먼저 확인 필요.

### 4.4 `/control` ReadTimeout 반복 크래시

여러 세션에서 `requests.post(.../control)`이 5초 타임아웃 후 `ReadTimeout`으로 죽는 걸
반복 관찰. 로그 분석: 죽기 직전 `latency_ms`가 302→860→1128→707ms로 점점 느려지다 결국
타임아웃 — 점진적 열화 패턴. `nvidia-smi` 확인 결과 GPU는 15MB만 사용 중(멀쩡함, 두 모델
동시 로딩 때문이 아님). 대신 **`hypercorn main:app`(진짜 SDK 서버, `forodobot_semantic_nav/
main.py`) 프로세스가 16:38부터 한 번도 재시작 없이 오늘 배포 세션 10개 이상을 전부 같은
헤드리스 브라우저/Agora 세션으로 처리하고 있었음**을 확인 — 장시간 유지된 WebRTC/헤드리스
브라우저 세션의 전형적인 열화 패턴과 일치. **결론: SDK 서버(`main.py`) 쪽을 재시작하면
해결될 가능성이 높음** (우리 배포 스크립트 재시작만으론 안 풀림 — SDK 서버는 별도
프로세스라 그대로 유지되기 때문).

**코드상의 별도 공백(아직 미수정)**: `run()`의 메인 루프에서 실제 명령을 보내는
`self.send_control(sent_linear, sent_angular)` 호출이 `step()` 실패를 잡는 try/except **밖에**
있어서, 이 호출 자체가 실패하면 `except KeyboardInterrupt`에도 안 걸리고 **정지 시도조차
없이 프로세스가 바로 죽는다.** 다음 세션에서 이 호출도 try/except로 감싸서 최소 한 번은
정지 재시도를 하도록 고치는 게 좋음(사용자에게 제안했으나 아직 진행 여부 확답 전).

## 7. Known limitation / 다음 할 일

1. `_goal_reached`(GPS latch)가 SEMANTIC_NAV에도 적용됨 — semantic이 별개 목표를 향해가도
   원래 GPS 목표 근처에서 멈출 수 있음 (§4.2, 미수정).
2. `heading_trustworthy`/`_last_map_heading_source`가 MAP_NAV를 벗어나면 마지막 값에 고정된
   채 SEMANTIC_NAV 게이트에도 영향을 줌 — 대부분 안전 쪽으로만 작동하지만 예상 밖으로 막힐
   수 있음.
3. `ABORT`가 `control_stage`만 되돌리고 `nav_mode`는 안 되돌림 — 재개 시 SEMANTIC_NAV부터
   바로 시작될 수 있음(안전엔 문제없으나 인지 필요).
4. `forodobot_semantic_nav/policy/calibration.json` 없음 — 현재 속도 스케일이 placeholder값.
5. `run()`의 마지막 `send_control()` 호출이 예외 처리 밖에 있어 SDK 타임아웃 시 정지 시도
   없이 크래시함(§4.4, 미수정, 다음 세션 우선순위).
6. 좌회전 편향의 근본 해결(재학습/클래스 리밸런싱)은 CLAUDE.md에 이미 있던 계획대로 아직
   해야 함 — 오늘 추가한 bias/override는 전부 임시 실험값.
7. SEMANTIC_NAV 진입 후 "도착(DONE)" 자동 감지 로직 없음(비전 기반 도착 감지가 애초에
   forodobot_semantic_nav에 없음) — 운영자 수동 개입 또는 GPS latch(§4.2와 같은 메커니즘)에
   의존.
8. GPS 신뢰도(§4.3) — 특정 물리적 지점에서 fix가 반복적으로 얼어붙는 문제, 코드로 해결
   불가(하드웨어/환경 이슈), 실측으로 재확인 필요.

## 8. 실제 로봇에서 다음에 할 일

1. SDK 서버(`hypercorn main:app`) 재시작 후 재시도 — §4.4 가설 검증.
2. GPS가 얼어붙었던 그 지점에서 fix_quality가 실제로 개선되는지(개활지 이동 등) 확인.
3. `--map_angular_override_rad_s 0.0`으로 순수 직진 구간에서 linear만 정상 작동하는지 먼저
   검증.
4. 위가 안정되면 `--semantic_switch_distance_m`을 실측으로 좁혀가며(8→3→...) 실제 전환 지점
   결정.
5. §4.1(좌회전)·§4.2(GPS latch)는 필요 시 다음 세션에서 코드로 다룰 것.
