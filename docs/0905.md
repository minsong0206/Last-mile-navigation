## 배경 — 왜 이 작업을 시작했나

목표는 "규격서를 얼마나 완벽히 따르느냐"가 아니라 **FrodoBot Mini가 실제로 잘 주행하도록,
모델이 배포 시 받는 지도를 학습 때와 최대한 동일하게 만드는 것**이다. 이 관점에서 두 가지를
동시에 손보기로 했다:

1. `MAP_RANGE_M`(맵 스케일)이 정중앙 대칭 크롭이라 전방 시야가 부족한 문제 — 예전에
   `TalkFile_map_image_spec(2).zip`(맵 렌더링 규격서, `C:\Users\minso\Downloads`에 있음,
   `C:\Users\minso\AppData\Local\Temp\map_spec_extract\map_image_spec\`에 압축 해제해둠)를 참고해서
   앵커/스케일을 재검토하던 게 지난 세션에서 끝을 못 냄.
2. waypoint 예측 horizon이 실제로는 약 2m밖에 안 됨(`N_WAYPOINTS=8`, `WAYPOINT_STRIDE=3`) — 5~8m로
   늘리고 싶다는 요청.

## 결정된 것 (재확인용)

- **맵 스케일**: "B안(배포 튜닝)" 채택 — 전방 20m(기존 검증값 유지) / 후방 7m / 좌우 약±13.5m.
  규격서의 "0.25m/px 고정, 56x56m 커버리지"(A안)는 채택 안 함 — 96px 모델 입력 기준 유효 해상도가
  기존 대비 두 배 가까이 거칠어지기 때문(반면 B안은 기존 검증된 유효 해상도~0.28m/px 유지).
- **waypoint horizon**: 5m 채택 (8m 아님) → `WAYPOINT_STRIDE=7`.
- **배포 heading 소스**: 지금 바로 GPS궤적 기반으로 전환(다음 실주행까지 미루지 않음).

## 변경된 파일

### `osm_pipeline/py/osm_map_generator.py` (학습+배포 공용 렌더러 — 여기 하나만 고치면
`build_live_map.py`가 `render_frame`/`build_canvas`를 직접 import해서 쓰므로 학습/배포 양쪽에
자동 반영됨)

- `MAP_RANGE_M`의 **의미가 half-width → 전방 reach(m)로 바뀜**. `REAR_RATIO=0.35` 상수 신설
  (`rear_m = MAP_RANGE_M * REAR_RATIO`). 스케일(m/px) = `(전방+후방)/MAP_SIZE_PX`로 유일하게 결정되고
  좌우 half-width는 `(전방+후방)/2`로 자동 파생됨(별도 파라미터 아님, out_size가 정사각형이라
  단일 등방 스케일만 가능하기 때문).
  - 기본값 `MAP_RANGE_M=20.0` → 전방20m/후방7m/스케일≈0.1205m/px/좌우half-width≈13.5m.
- `ZOOM` 18→19.
- 타일 provider: `tile.openstreetmap.org` → `basemaps.cartocdn.com/rastertiles/voyager_nolabels`
  (규격서 5절: "다른 provider 타일이 캐시에 섞였던 실제 사고 사례" 참고해서 `TILE_CACHE`도
  provider별 서브디렉토리로 분리 — `tile_cache/cartocdn_voyager_nolabels/`).
- `render_frame()` 전면 재작성: 기존엔 "회전(warpAffine, scale=1) → 정사각형 crop → 별도 resize"
  3단계라 리샘플이 2번 일어남(규격서가 명시적으로 금지하는 패턴). 지금은 회전+리스케일+앵커배치를
  **`getRotationMatrix2D`로 만든 스케일+회전 행렬을 ego점 기준으로 평행이동만 추가해서 단일
  `warpAffine`(bicubic)**로 합성 — 리샘플 1회. 회전 공식(`rot_deg = 90 - heading_deg`) 자체는 기존에
  검증된 걸 그대로 재사용(바꾼 적 없음).
- robot(ego) 마커를 **warp 이후에** 그리도록 변경 — 위도/스케일과 무관하게 항상 고정 픽셀 크기
  (기존엔 warp 전에 그려서 회전 시 살짝 찌그러질 수 있었음).
- 지도 밖(캔버스 경계 밖) 채움색: 흰색(255,255,255) → 회색(200,200,200).
- **goal 마커 추가**: `future_route`의 마지막 점(=그 세그먼트의 진짜 목적지)에 원 마커. 기존 코드는
  `GOAL_DIST_M` 상수만 정의돼 있고 실제로는 전혀 그려지지 않는 버그였음.
- **과거 경로(회색선) 로직은 전혀 안 건드림** — 그리는 조건/좌표 계산 코드 그대로. 타일 provider
  교체와 과거 경로 렌더링은 완전히 독립적인 코드 경로다 (세션 중 이 부분을 혼동할까봐 확인차 재차
  검증함).
- `ROUTE_WIDTH`(경로선 두께, 교수님 피드백으로 이미 4→2로 확정됨)와 `GOAL_DIST_M` 자체는 안 바꿈.

### `deployment/build_live_map.py`

### `deployment/omnivla_edge_deploy.py`

- **heading 소스 전환**: `step()`에서 기존엔 IMU 컴퍼스(`heading_rad`)를 그대로
  `predict_waypoints()`에 넘겼는데, 이제 `estimate_heading_from_track(past_track)`으로 만든
  GPS궤적 기반 heading(`map_heading_rad`)을 우선 사용하고, 이동량 부족(정지/막 시작)으로 `None`이
  나올 때만 IMU로 폴백. 이유: 학습 데이터의 heading은 GPS궤적 기반(`atan2`)으로 만들어졌는데
  (`osm_map_generator_rides11.py::estimate_headings()`와 동일 공식), 배포는 IMU 컴퍼스를 썼고
  이 둘이 2026-08-25 실측(`docs/0825.md` 2-2)에서 평균 **+97°** 어긋남이 확인됐었음.
  `record["map_heading_source"]`에 `"gps_track"`/`"imu_fallback"` 로그 남김.
- `estimate_heading_from_track()` 자체도 수정: 기존엔 "직전 2개 GPS 점"만 비교해서 GPS가
  ~0.42m 단위로만 갱신되는 양자화 잡음에 취약했음(`docs/0825.md` 1-1에서 시각화 스크립트 쪽은 이미
  이 문제로 "누적 1.5m 이상 구간" 방식으로 고쳐졌던 전례가 있음) — 지금까지는 진단(로그 출력)용이라
  괜찮았지만 이제 실제 제어에 쓰는 값이 되므로 같은 방식으로 수정(`min_disp_m` 기본값도 0.3→1.5).
- `CTX_STRIDE_SEC`(컨텍스트 이미지 캡처 간격, 0.3초 유지)와 `WAYPOINT_STRIDE_SEC`(waypoint 간
  시간 간격)을 **분리된 별도 상수**로 신설. 기존엔 우연히 둘 다 3프레임=0.3초라 `CTX_STRIDE_SEC`
  하나를 두 용도(프레임 버퍼링 + `waypoint_to_control()`의 시간 분모)에 같이 썼는데, waypoint
  horizon을 5m로 늘리면서 `WAYPOINT_STRIDE`가 7로 바뀌어 두 값이 갈라짐 — 그대로 뒀으면
  `waypoint_to_control()`이 잘못된 시간으로 나눠서 2026-08 "명령이 항상 작게 나오는" 버그가
  똑같이 재발했을 것. `WAYPOINT_STRIDE_SEC=0.7`로 설정, 기존 25/12/20m 체크포인트로 되돌아가서
  쓸 땐 다시 0.3으로 되돌려야 함(docstring에 명시).

### `osm_pipeline/py/rides11_dataset.py`

- `WAYPOINT_STRIDE` 3→7. 근거: 선택된 538개 세그먼트의 valid-frame 구간(EKF `filtered_position`
  기준) 실측 평균속도 **0.90 m/s**(median 0.89, p25~p75: 0.79~0.97) — 계산 스크립트는 세션 중
  1회성으로 작성해서 실행하고 지우지 않음(필요하면 재작성 가능, 로직: `episode_selector.split_into_segments`
  로 세그먼트 나눈 뒤 valid 구간[`PAST_MARGIN:len-FUTURE_MARGIN`]의 누적이동거리/누적시간).
  `WAYPOINT_STRIDE=7`(0.7초/step) × 8 waypoints × 0.90m/s ≈ 5m.
- `N_WAYPOINTS=8`은 안 바꿈 — 모델 아키텍처(예측 head 크기)에 묶여 있어서 바꾸면 `strict=True`
  체크포인트 로드가 깨짐(재학습이 아니라 아키텍처 변경이 필요).

## 검증한 것 / 안 한 것

**검증 완료** (합성 캔버스로, 네트워크 타일 없이):
- ego가 정확히 앵커 픽셀(224px 기준 `(112, 165.9)`)에 위치.
- 전방/후방 reach가 공식대로 나옴 (전방 165.9px=20m, 후방 58.1px=7m).
- 회전 방향: heading=90°(정북 주행)에서 무회전(identity) — 정북 주행이면 지도 자체가 이미
  north-up이라 회전 불필요하므로 당연히 맞음. heading=-90°(정남 주행)에서 정확히 180° 뒤집힘.
  두 독립적인 케이스가 모두 일치해서 기존에 검증된 회전 공식이 스케일 추가 후에도 안 깨졌음을 확인.

**아직 안 한 것 (다음 세션/실행 시 필요)**:
1. **실제 타일로 재생성 테스트** — `python3 osm_pipeline/py/osm_map_generator.py --ep <아무 episode>`로
   에피소드 1개만 뽑아서 눈으로 확인 (cartocdn 타일이 실제로 잘 받아지는지, OSRM 서버 켜져 있어야 함
   — Perth~Madrid + Seoul:5011 포트 매핑은 `osrm_port()` 참고).
2. **전체 재처리** — 538개 세그먼트 전부, 몇 시간 소요 예상 (지난 세션에서 병목 분석한 대로 EKF/OSRM은
   안 무겁고 OSM 타일 렌더링이 병목).
3. **재학습** — `WAYPOINT_STRIDE`/맵 스케일 둘 다 바뀌었으므로 처음부터 다시.
4. **실기기 재검증** — 다음 실주행에서:
   - `heading_diff_deg`/`map_heading_source` 로그로 GPS궤적 heading이 잘 나오는지(이동량 부족으로
     계속 `imu_fallback`만 찍히면 `min_disp_m=1.5`가 너무 커서 못 채우는 것일 수 있음 — 로그 확인).
   - 2026-08-10 배포에서 관찰된 좌회전 편향이 줄었는지.
   - waypoint 예측거리/실제 전진거리 비율(`docs/0825.md` 2-3, 예측의 약 30%만 실제 전진했던 문제)이
     그대로인지 — 이건 오늘 작업과 무관한 별개 이슈(주로 `MAX_V=0.3` 안전캡 때문, 미해결).

## 오늘 다루지 않은, 여전히 열려있는 이슈

- **과거 경로 cold-start 불일치**: 학습 데이터는 모든 프레임이 `PAST_MARGIN=15`(→ 이제 프레임 수
  자체는 안 바뀜, waypoint 쪽만 바뀜) 이상의 과거 경로를 항상 가짐. 배포는 `past_track`이 매
  배포 시작 시 빈 리스트에서 시작해서 처음 몇 tick은 과거 경로(회색선) 없이 렌더링됨 — 구조적
  분포 차이, 오늘 손 안 댐.
- **미래 경로 GT vs OSRM 불일치**: 학습은 그 세그먼트의 실제 GT GPS 궤적을 미래 경로로 씀, 배포는
  목적지까지 OSRM으로 미리 계산한 최단경로를 씀 — 두 경로가 실제로 얼마나 다른지 아직 실측 안 함
  (지난 세션에서 "검증 필요"로 남겨둔 항목, `docs/0825.md`에도 재언급됨).
- **`MAX_V=0.3` 안전캡으로 인한 속도 손실**(`docs/0825.md` 2-3) — 모델이 기대하는 속도(0.861m/s)의
  35%밖에 안 됨. 오늘 작업과 별개, 안전 여유 확인 후 단계적으로 올려보는 실험 필요.
