# 재학습 계획 (2026-11-01 작성)

`docs/1101_report.md`의 결론을 바탕으로 한 OmniVLA-Edge(odom3ch) 재학습 계획. 아직 실행 전.

## 원칙

오늘까지 확인한 경로 이탈 원인의 대부분은 **모델 구조가 아니라 "학습 때 본 입력과 배포 때 보는 입력의
차이"**였다. 그래서 재학습은 모델을 바꾸기보다 입력 분포를 배포 조건에 맞추는 데 집중한다.

로봇 반응 특성(±0.05 반응 없음 구간, 회전 1.66배)은 배포 쪽 명령 변환 보정
(`--enable_actuation_calibration`)으로 처리했으므로 학습 대상이 아니다. 하드웨어 좌편향도 기계
문제라 데이터로 고칠 대상이 아니다. 모델은 "어디로 갈지(waypoint)"만 잘 예측하면 된다.

## 1. 지도 입력을 배포 조건과 맞추기 (최우선)

### 1-1. 경로 선 (GT vs OSRM)

| | 학습 | 배포 |
|---|---|---|
| 지도 위 빨간 경로 | 로봇이 실제로 간 미래 경로(GT) | OSRM 경로 |
| 특징 | 항상 로봇 위치에서 시작, 실제 움직임과 일치 | 실제 보도와 5~10 m 어긋나거나 엉뚱하게 꺾임 (직선 90 m → 185 m 사례, `docs/1011_dead_reckoning.md` §2) |

- **경로 섭동 증강:** 학습 지도의 경로를 무작위로 흔든다 — 옆으로 1~5 m 평행 이동, 각도 ±5~10°,
  꺾이는 지점 앞뒤 이동.
- **OSRM 경로 섞기:** 가능하면 학습 에피소드의 시작/끝 좌표로 OSRM 경로를 다시 뽑아 일부 샘플에
  GT 대신 사용 (OSRM 서버 포트 5011, `osm_pipeline/py/osm_map_generator.py::osrm_port()`).

### 1-2. heading 잡음

- 학습 heading = "현재 GPS 점 → 다음 GPS 점" 방향
  (`osm_pipeline/osm_data/output_rides_11/osm_map_generator_rides11.py::estimate_headings`).
- 배포 heading은 실제 진행방향과 중앙값 44° 차이가 난 적이 있다(10/11, `route_bearing_anchor`).
- **회전 증강:** 학습 지도를 ±10~20° 무작위 회전. 너무 크게 주면 모델이 지도를 덜 믿게 되므로,
  배포에 자이로 기반 heading(오프라인 직선 오차 2.6~3.2°)을 넣는 계획과 맞춰 작게 시작한다.

### 1-3. 지도 생성 코드 통일

- 학습 지도와 배포 지도를 **같은 렌더링 코드**로 만든다 (축척, 로봇 앵커 위치, 회전 방식).
- 9/5에 지도 기하가 "정중앙 대칭"에서 "전방 reach + 후방 `REAR_RATIO`"로 바뀌었다(`docs/0905.md`).
  재학습 체크포인트는 새 기하로 통일하고, `--map_range`를 학습값과 반드시 일치시킨다.
- 9/6 재생성 때 타일 서버가 API 키를 요구하면서 "API KEY REQUIRED" 워터마크가 섞였다(`docs/0906.md`).
  **재생성 전에 타일 소스 문제부터 해결**하고, 샘플 몇 개를 눈으로 확인한 뒤 전체를 돌린다.

## 2. 좌우 균형과 회전 데이터

현재 학습 데이터: 직진 10.6%, 우회전:좌회전 = 1.53:1. 실주행에서 모델의 작은 좌편향(+0.0115)과
우회전 출력이 약한 경향(같은 회전 요구에 좌회전의 41~72%, `docs/1011.md` §3)이 관찰됐다.

- **좌우 반전 증강 (추천):** 카메라 이미지 좌우 반전 + 지도 좌우 반전 + 정답 waypoint의 좌우 좌표
  부호 반전을 함께 적용. 좌우 균형이 정확히 맞아 편향 원인 하나가 구조적으로 사라진다.
  - 주의: 이미지·지도·waypoint 셋을 **반드시 같이** 뒤집을 것. 하나라도 빠지면 오히려 편향을 학습함.
  - 문맥 이미지(과거 프레임)도 전부 같이 뒤집는다.
- **회전 구간 가중치:** 회전 구간을 더 자주 뽑거나(oversampling) 손실 가중치를 준다.
- **평가 분리:** 직진 구간과 회전 구간을 따로 평가한다. 지금은 전체 평균(ADE 등)만 봐서 회전 성능이
  가려진다.

## 3. 우리 로봇·배포 지역 데이터 추가 (파인튜닝용)

rides_11 데이터의 로봇·카메라·환경과 FrodoBot Mini 배포 환경(카메라 높이·화각, 서울과기대 보도)은
다르다.

- **수집 방법:** 관측 전용 모드(`--observe_only`)로 사람이 원격조종하면 카메라 이미지, GPS, 자이로,
  rpm, 모델 입력 지도가 전부 `deployment/logs/`에 남는다. 학습 데이터 형식과 거의 같다.
- **정답 경로:** 사람이 실제로 간 궤적. GPS가 거칠면 오프라인 필터
  (`deployment/analysis/imu_gps_fusion_replay.py`의 complementary/EKF)로 다듬어서 쓴다.
- **분량:** 배포할 동선에서 회전 위주로 수십 개 에피소드부터.
- 실험 B(관측 전용 + 사람 조종)를 하면서 함께 모은다.

## 4. 재학습 전에 할 일

1. **기준선 만들기:** 현재 체크포인트로 회전 구간만 따로 오프라인 평가 → 재학습 효과를 숫자로 비교할 기준.
2. **원본 데이터 편향 확인:** `docs/experiment_log.md` §1-3(원본 Arrow 데이터 좌편향 직접 확인)이 아직
   막혀 있다. 데이터 자체에 좌우 편향이 있는지 먼저 보면 좌우 반전 증강의 필요성을 판단할 수 있다.
3. **배포 쪽 정리 먼저:** 실외 테스트 C(명령 변환 보정)와 자이로 기반 heading이 확인돼야, 재학습
   후 실주행에서 남는 오차를 모델 탓으로 해석할 수 있다.
