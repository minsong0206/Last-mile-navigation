실험일 2026-08-22 지역 서울과기대 (37.631, 127.076) 맵 반경 20m 체크포인트 odom_20m

Heading Rotation Audit

OmniVLA-Edge 배포 파이프라인에서 로봇 헤딩이 지도 회전에 올바르게 반영되는지 검증한 기록. render_frame()의 회전 공식 자체를 실제 OSM 타일 위에서 재확인하고, omnivla_edge_deploy.py에 적용한 orientation → heading 변환 수정이 지도 방향에 어떤 차이를 만드는지 같은 좌표로 비교했다.

01

이 실험이 검증하는 것

우선순위 2는 사실 두 개의 서로 다른 질문을 담고 있다. 하나는 "회전 공식 자체가 맞는가", 다른 하나는 "고친 orientation 변환이 실제로 90°를 되돌려주는가". 아래 두 세트는 각각 이 질문 하나씩에 답한다.

실험 A 회전 공식 단독 검증 — deployment/build_live_map.py의 --heading_deg를 0/90/180/270으로 직접 주입해서 render_frame() (osm_map_generator.py:152-237)만 따로 떼어 테스트. 이 값은 poll_frodobot()의 변환식을 거치지 않고 바로 회전 공식에 꽂히므로, 1번 수정과는 무관하게 "동-0°/북-90°/CCW 회전 자체가 맞는가"만 확인한다.
실험 B 수정 전/후 비교 — 로봇 컴퍼스가 orientation=0°/90°/180°/270° (진북/동/남/서 가정)를 읽었다고 시뮬레이션하고, 그 값을 실제로 수정 전 공식(-orientation)과 수정 후 공식 (90-orientation) 각각에 통과시켜 나온 지도를 나란히 놓았다. 이게 실제로 1번 수정이 무엇을 바꿨는지 보여주는 쪽이다.
좌표 2026-08-10 실배포 로그(deploy_20260810_223436.jsonl)의 실제 출발/목표 GPS를 그대로 재사용 (서울과학기술대 인근).
주의 섹션 2·3(실험 A·B)은 OSRM 로컬 서버(5011)가 꺼진 상태에서 생성돼 query_osrm_route()가 직선 경로 폴백으로 대체됐음 (build_live_map.py:100-102) — 회전/좌표축 검증에는 문제 없지만 빨간 선의 실제 굴곡(보행로 형태)은 반영되지 않았다. 섹션 6(실험 D)은 이후 Seoul OSRM docker(osm_pipeline/osrm/seoul/, port 5011)를 실제로 띄운 뒤 재생성한 것이라 실제 보행로를 따라가는 경로다.
02

실험 A — 회전 공식 단독 검증

같은 캔버스·같은 경로에서 heading_deg만 90°씩 바꿔 4장을 뽑았다. 네 장을 90°씩 서로 돌려 겹쳤을 때 도로/건물 윤곽이 일치하면 회전 공식은 결백하다 — 이미 verify_map_coordinate_axes.py 합성 테스트로 확인된 결과를, 이번엔 실제 타일 위에서 재확인하는 것.

판정: 네 장 모두 초록 ego 마커와 빨간 경로선의 상대 각도가 정확히 90°씩만 다르고 형태·굴곡은 동일 — rot_deg = 90 - heading_deg 공식은 실제 타일에서도 정상 동작한다. 즉 2번 항목의 버그는 이 회전 공식이 아니라, 여기 들어가는 heading 값을 만드는 쪽(실험 B)에 있었다.

위 실험은 로봇 없이 좌표만으로 돌린 오프라인 테스트라, 지금 이 페이지엔 표시할 "실시간 대시보드"가 없다. 대시보드(deployment/debug_web.py)는 omnivla_edge_deploy.py가 실제로 돌고 있을 때만 뜨는 별도 로컬 웹서버다. 다음 실주행에서 이렇게 확인하면 된다.

실험 C — 실제 주행 로그로 사후검증

섹션 2·3은 좌표만 가지고 돌린 오프라인 테스트였고, orientation의 의미(진북=0°, 시계방향)도 다른 스크립트에서 추론한 가정이었다. 이번엔 가정을 걷어내고 실제로 로봇이 움직인 deploy_20260810_223436.jsonl (수정 전 코드로 기록됨) 하나로 검증한다. 매 tick마다 로봇 컴퍼스 값(orientation)과 로봇이 실제로 이동한 두 GPS 점으로 계산한 진짜 이동방향 (gps_heading_deg, estimate_heading_from_track())이 둘 다 이미 로그에 남아있다 — 이 둘의 차이가 "지도 위쪽이 실제로 로봇이 가는 방향과 맞는가"를 가장 직접적으로 answer하는 값이다.
